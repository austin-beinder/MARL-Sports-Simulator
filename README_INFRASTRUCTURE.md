# Overall Infrastructure — Issue #10

This document is generated by ChatGPT.

This document explains the infrastructure files added for the **Overall
infrastructure** issue and how they fit the repository's existing code.

The goal is not to implement the environment or reinforcement-learning
algorithm. The goal is to provide the application "glue" that lets those parts
run from a reproducible configuration.

---

## 1. What already existed

The repository already has a working `KeepAwayEnv` with a Gym-like interface:

```python
observation, info = env.reset(seed=...)
observation, reward, terminated, truncated, info = env.step(action)
env.close()
```

`KeepAwayEnv` already owns the PyBullet connection and physics stepping.

That ownership is important: **the infrastructure must not create a second
PyBullet connection**.

The existing joystick also produces the same basic 2-D velocity command shape
that the environment accepts from the RL layer.

## 5. Output layout

Each run creates its own directory:

```text
outputs/
  <timestamp>-<project>-<mode>/
    config.yaml
    run_metadata.json
    metrics.csv
    checkpoints/
```

### Why save the YAML again?

RL experiments are sensitive to small configuration changes.

Keeping the exact config that produced a run makes it possible to later answer:

> "Which settings produced this result?"

without relying on memory or Git history alone.

---

## 6. Configuration ownership

The YAML file has two different kinds of settings.

### Infrastructure-owned settings

Examples:

```yaml
simulation:
  gui: false

logging:
  output_dir: "outputs"

training:
  learning_rate: 0.0003
```

These are loaded by `config.py`.

### Environment-owned settings

Everything under:

```yaml
game:
  config:
```

currently maps directly to the existing `KeepAwayConfig`.

For example:

```yaml
game:
  config:
    blue_max_speed: 3.0
    field_length: 21.0
    action_repeat: 8
```

becomes conceptually:

```python
KeepAwayConfig(
    blue_max_speed=3.0,
    field_length=21.0,
    action_repeat=8,
)
```

This avoids creating a second copy of the game configuration schema.

## 7. Why there is a demo mode

The repository does not need to wait for PPO/IPPO/MAPPO to test Issue #10.

Demo mode uses the real `KeepAwayEnv` but feeds it a simple policy:

- `random`
- `stationary`

This verifies:

```text
YAML
 -> main
 -> environment
 -> reset/step
 -> CSV output
 -> clean shutdown
```

without pretending that learning has already been implemented.

## 8. RL integration

When the RL issue provides a trainer function, YAML can switch to:

```yaml
run:
  mode: "rl"

training:
  entrypoint: "train:run"
```

The current **provisional** contract is:

```python
def run(env, config, context):
    ...
```

The RL code gets:

- `env` — the already-created environment
- `config` — parsed experiment settings
- `context.run_dir`
- `context.checkpoints_dir`
- `context.metrics_path`

### Important

The repository has a separate **Define Gym/RL layer API/ICD** issue.

That issue should review this function signature before it becomes permanent.
If the agreed API changes, the goal is to update `rl_bridge.py` rather than
rewriting `main.py`.

## 9. Checkpoint helpers

`checkpoints.py` provides generic helpers for a future PyTorch trainer.

It can save:

```text
model weights
optimizer state
episode number
extra metadata
```

It does **not** define:

- PPO
- IPPO
- MAPPO
- policy architecture
- critic architecture

Those are RL-layer responsibilities.

PyTorch is intentionally imported only when a checkpoint function is used,
because the repository has not yet committed to it as a dependency.

## 10. Debugging

The existing `KeepAwayEnv` already creates the GUI and sets a camera in human
mode.

`debug_tools.py` only customizes that existing GUI. It does not create another
PyBullet connection.

Current debug features:

- top-down-ish configurable camera
- hide PyBullet side controls
- player labels
- deterministic YAML/seed setup

The existing joystick is also useful as a manual behavior debugger because its
output matches the current environment action format.

A useful future pattern is to add scenario configs such as:

```text
configs/scenarios/
  contested_ball.yaml
  wall_collision.yaml
  kickoff.yaml
```

so teammates can reproduce bugs from a known setup.

## 11. Current repository import warning

The source folder is currently named:

```text
pybullet/
```

while the external physics dependency is also imported as:

```python
import pybullet as p
```

The current repository uses script-style sibling imports such as:

```python
from ball import Ball
```

For that reason, **do not add `pybullet/__init__.py`** as part of this issue.

Turning the local directory into a package named `pybullet` can shadow the
third-party library.

A future cleanup could rename the source folder to something like:

```text
simulator/
soccer_sim/
marl_sports/
```

but that refactor should be coordinated with the team because it touches many
imports.

## 15. Short explanation for peer review

A concise explanation is:

> The infrastructure layer gives the project one repeatable way to start and
> run experiments. YAML controls environment, debug, and future RL parameters.
> `main.py` handles process-level setup, `runner.py` creates the existing
> environment, output directories and metrics are standardized, and the RL
> bridge provides a small integration point for the future trainer. The
> environment still owns PyBullet and game logic, so the layers stay separated.
